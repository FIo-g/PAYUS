## 1. 백엔드 아키텍처 개요

세종페이 백엔드는 **Node.js 20 + Express + Mongoose(MongoDB Atlas)** 기반의 레이어드 아키텍처로 설계되었다. 요청은 `routes → controllers → services → models`의 단방향 흐름을 따르며, 보안·로깅·검증·에러 처리는 횡단 관심사(`middlewares/`, `utils/`, `config/`)로 분리된다. 결제와 같은 핵심 비즈니스 로직은 컨트롤러에서 분리해 `services/` 계층에 위치시켜, 트랜잭션 무결성과 단위 테스트 용이성을 확보하였다.

모든 API는 `{ success, data?, error?: { code, message } }`의 단일 응답 봉투와 13종 표준 에러 코드(`AppError` 계층, `code`+HTTP status 동시 보유)를 사용한다. 보안 계층으로 `helmet`, CORS 화이트리스트, 라우트별 요청 제한(결제 라우트 분당 10회, 일반 분당 100회)을 적용하였다. 정식 디렉터리 규약은 `sejongpay/backend/`로 통일하였다.

## 2. 구현 완료 기능 (검증 완료)

- **결제 트랜잭션 엔진(11단계)** — `POST /transactions/payment`. 멱등성 보장(`idempotencyKey` 부분 유니크 인덱스 + 트랜잭션 자동 재시도), 원자적 잔액 차감(`$gte` compare-and-set), 불변 원장(append-only) 기록, `balanceBefore/After` 스냅샷 정합, 정수 단위 캐시백(`Math.floor`), 쿠폰 검증·원자적 사용 처리.
- **동적 QR 보안 모듈** — `POST /merchants/:id/qrcode/dynamic`. HMAC-SHA256(가맹점별 비밀키) 서명 + 10분 만료 + 일회성 nonce + `crypto.timingSafeEqual` 비교. 가맹점 식별자는 서명 검증된 토큰에서만 도출하여 클라이언트 위조를 차단한다.
- **거래 조회 API** — `GET /transactions`(커서 기반 페이지네이션, 유형·기간 필터, 본인 거래 한정), `GET /transactions/:id`(영수증 상세, 정보 유출 방지 404).
- **인프라·문서** — Express 부트스트랩(앱/서버, 전역 에러 핸들러), 7개 컬렉션 Mongoose 모델 인터페이스, OpenAPI 3 명세, 공통 규약 문서(`CLAUDE.md`, `CONVENTIONS.md`).
- **검증** — 인메모리 MongoDB 복제셋(MongoMemoryReplSet) 위에서 **실제 트랜잭션 기반 동시성·정합성 테스트 26건 전부 통과**(과차감 경합, 동일 키 5건 동시 요청의 단일 처리, QR 재사용 차단, 전체 롤백, 원장 재조정 등).

## 4. 기술적 도전과제

### 4.1 동시성 제어
같은 사용자의 동시 결제, 동일 `idempotencyKey`의 동시 다중 요청에서 **중복 차감 없이 단 1건만 처리**되어야 한다. MongoDB 세션 트랜잭션, 원자적 compare-and-set(`$gte` 가드), 부분 유니크 인덱스, 그리고 일시적 트랜잭션 충돌(WriteConflict)에 대한 자동 재시도를 결합해 해결하였다. 특히 초기 구현이 중복 키 오류(E11000)만 처리하고 쓰기 충돌(코드 112)을 놓치던 결함을 적대적 코드 리뷰로 발견·수정하였다.

### 4.2 결제 정합성
잔액 캐시(`walletBalance`)와 거래 원장(`Transactions`) 합산이 항상 일치해야 한다. 모든 거래행에 `balanceBefore/After`를 기록하고 원장을 불변(append-only)으로 유지하여 재조정 가능성을 보장하였다. 모든 금액은 정수(원) 단위로 강제하고 부동소수점 연산을 금지(`Math.floor`)하여 캐시백·쿠폰 할인의 정밀도 손실을 차단하였다.

### 4.3 QR 보안
정적·동적 QR 위조, 캡처 후 재사용, 타이밍 공격에 대응해야 한다. HMAC-SHA256 서명, 10분 만료, 일회성 nonce, 상수 시간 비교를 적용하였다. 특히 nonce 소비를 결제 트랜잭션 **밖**의 커밋된 쓰기로 분리하여, 결제 실패(롤백) 시에도 QR이 재사용되어 캐시백이 반복 지급되는 보안 결함을 차단하였다(적대적 리뷰로 발견·수정).

### 4.4 검증 방법론
결제·보안 코드는 "계획 → 사람 승인 → 신규 컨텍스트 적대적 리뷰(보안·정합성 2개 관점) → 실 DB 동시성 테스트 → 사람 리뷰"의 단계적 게이트를 적용하였다. 이 과정에서 실제 보안·정합성 결함 3종(QR 재사용, 쓰기 충돌 멱등성, QR 비밀키 강제)을 통합 이전에 사전 차단하였다.
